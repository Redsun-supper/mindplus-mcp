## 修复轮（已改代码 + 实测）

### 实测方法
本机 Mind+ 2.0.7 正在运行（`mind-link` 监听 19302/19303），直接读 `D:\Program Files\Mind+\apps\deps\mind-link\main.js`（v2.0.2，49KB 单行 bundle）做 substring 提取，逐条核对参数形状；再用 `ws` 子协议 `Serialport` 直连实测失败信号。

### 实证结论（重要，后续别重复踩）
- `replacePath` = `str.replace("%HOMEDIR%",homedir()).replace("%APPROOT%",process.cwd())`，**只替换首次出现**；仅作用于 `readFile/writeFile/readdir/mkdir/rmdir/unlink/stat/writeImgFile` 8 个方法。`rename` / `downloadFile` / `unzip` **不展开**占位符 → 必须传绝对路径。
- 所有控制口参数形状与实现一致：`rename{oldPath,newPath}`、`writeFile{fileName,content,flag}`、`mkdir/rmdir{path,options}`、`downloadFile{url,targetPath}`、`unzip{zipFile,unzipPath}`、`stat/unlink/access/exists{path}`、`readdir{path,options}`。`exists` 返回布尔。
- 串口：坏端口发 `error` 通知（`Error: Opening COM255: File not found`）随后销毁 WS；SerialPort 自身 `close` 事件才发 `close` 通知。**原「白等满超时」的判断是错的**——`onClose` 已兜住；`close` 分支加固仍保留（防御性）。
- Mind+ 数据目录 `getAppDataPath()` = `%HOMEDIR%\AppData\Local\mind+`（win）/ `~/Library/mind+`（mac）/ `~/.mind+`（linux）；`ARDUINO_PATH = <data>/Arduino`。原代码路径**本来就对**。
- **Mind+ 用 `--config-file <data>/Arduino/arduino-cli.yaml` 驱动 arduino-cli，不是 `ARDUINO_DIRECTORIES_DATA`**（env 只能修 `directories.data`，`directories.user` 会跑偏到 `~/Documents/Arduino`）。

### 改动
- `src/index.js`：instructions `mindplus_info`→`info`，并写明占位符适用范围。
- `src/tools.js`：新增 `mindPlusDataDir()`；`SerialSession` 的 `close` 通知改为 reject `openWaiters`；`arduino_cli` 改为注入 `--config-file`（先 `exists` 探测，caller 传了就不覆盖）。
- `README.md`：新增「验证状态」表；补 %HOMEDIR% 展开范围警告；更新工具表、实测输出（smoke 11/11）。
- `test/smoke.mjs`：新增 fs mkdir/rename/stat/remove 往返、arduino_cli version + config dump、坏端口快速失败（实测 4ms）三项检查，7→11。

## 第二轮：包装全部剩余子协议（node-pty / ssh / MQTT / UDP）

工具数 18 → **44**。新增 `src/sessions.js`（5 个会话类，SerialSession 从 tools.js 迁入），tools.js 只留工具目录。

### 新增工具（26 个）
- pty 7：`pty_open/read/write/resize/pause/resume/kill`
- ssh 7：`ssh_connect/exec/shell_open/shell_write/shell_read/sftp/disconnect`（`ssh_sftp` 用 `op` 枚举覆盖 8 个 SFTP 操作）
- mqtt 5：`mqtt_connect/subscribe/publish/read/disconnect`
- udp 6：`udp_open/bind/send/set_broadcast/read/close`
- 1：`sessions_status`（五通道总览）

### 各子协议的坑（实测/bundle 核验）
- **ssh2 v1.16.0 的 `Config` 缺 `username` 会同步抛错** → mind-link 的 `didReceiveCall` 抛出 → **整条调用被静默丢弃，不回复**（表现为 8s 超时）。已在 `ssh_connect` 预检 `username` 必填。**这是本轮最大的坑。**
- ssh 的 `error` 通知 params **恒为 undefined**（bundle 里 `reportError(e){…e.messgae}` 拼写错误）→ 连接被拒时拿不到底层原因。
- UDP `open` 通知是挂在 `dgram.createSocket` 的 **message 监听**上的 → 首个数据报到达才触发，不是 bind 时。以 `bindPort` 的 RPC 返回为准。
- UDP `sendUdpMessage` 的 `message` 直通 `dgram.send`；JSON 传不了 Buffer，`dgram.send` 又拒收普通数组 → **只能发文本**。
- node-pty 的 `spawn` 即发即忘（回复 null），`write` 的 params 是裸字符串，`resize` 用 `{cols,rows}`；`data` 是字符串、`exit` 是 `{exitCode,signal}`。
- MQTT `error` 通知 params 有真实文案（`reportErrorMessage(e=>e&&e.toString())`），与 ssh 不同。
- ssh 的 `end` 会 dispose 掉 WS，所以 `ssh_disconnect` 的 RPC 多半收不到回复（已 catch）。

### 实测
- pty：`cmd.exe /c echo pty-ok` 拿到输出 + `exitCode:0` ✅
- UDP：bind → send → 环回收到 `udp-smoke-ok` ✅
- ssh/mqtt 失败路径：结构化快速返回（3ms / 90ms）✅
- 未实测：成功的 SSH 登录、成功的 MQTT 会话（无 broker）、真实串口收发

### 测试
smoke 11 → **16 项**（+pty/udp/ssh/mqtt/sessions_status），http-smoke 的写死 18 改为 `>=40 + 家族存在性`。最终 **16/16 与 7/7 全绿**。
